<a id="local-checks"></a>

## Проверить проект локально

Потребуются Git, Python 3, Node.js 20+ и npm. Из терминала:

```bash
git clone https://github.com/Kazintsev/cashflow-gpt.git
cd cashflow-gpt
npm ci --ignore-scripts
npm run check:sql
npm run check:docs
npm test
```

`npm test` создаёт PostgreSQL в памяти через PGlite, устанавливает схему, загружает синтетический набор и выполняет 14 проверок. Подключение к рабочей базе и ключи Supabase для этого не нужны. При подготовке экспорта проверки прошли на PostgreSQL 18.3 (PGlite 0.5.8); это не тест внешнего PostgreSQL / Supabase или ИИ-адаптера.

<a id="install"></a>

## Установить SQL-ядро

Целевая версия — PostgreSQL 17+. Нужна отдельная база с **пустой схемой `public`** и подключение владельца схемы, который может создавать объекты и управлять их правами. Пользовательские расширения не требуются. Параметры подключения задаются вашим обычным профилем `psql` или окружением, без сохранения секретов в репозитории.

```bash
psql -X -v ON_ERROR_STOP=1 -f database/bootstrap.sql
psql -X -v ON_ERROR_STOP=1 -c 'SELECT public.get_status_until_next_income(now(), NULL);'
```

В новом проекте Supabase можно выполнить содержимое `database/bootstrap.sql` через SQL Editor от владельца. Если в `public` уже есть таблицы, функции, представления или последовательности, установщик выдаст ошибку до создания объектов. Это относится и к расширениям, разместившим свои функции в `public`: используйте отдельную чистую базу/проект с подходящей конфигурацией; установщик ничего не удаляет. После ошибки в интерактивной SQL-сессии выполните `ROLLBACK`.

Установка выполняется одной транзакцией, не добавляет прикладные записи и включает RLS на 19 таблицах. Чтение и запись предусмотрены от владельца; клиентские роли `anon`, `authenticated`, `service_role` не получают доступ. Чат и Data API этим шагом не подключаются. Подробности — в [описании исходников](source-code.md#access).

Это начальный bootstrap, а не миграция обновления существующего учёта. Точные файлы bootstrap и seed проверены 9 сентября 2026 года в отдельном проекте Supabase на PostgreSQL 17.6 через SQL-инструмент подключения. [Проверки и границы результата](testing.md#supabase-validation).

## Посмотреть вымышленный пример

В отдельной учебной копии после установки:

```bash
psql -X -v ON_ERROR_STOP=1 -f database/demo/seed.sql
psql -X -v ON_ERROR_STOP=1 -c 'SELECT public.get_status_until_next_income(now(), NULL);'
```

Набор задаёт банковский счёт, наличные, кредитку, платёжный буфер, долги, расход 450 ₽, ожидаемый доход и обеспеченный платёж. При чтении сразу после загрузки ожидаются `cash.actual_cash = 38750`, `weekly_budget.spend = 450`, `weekly_budget.budget = 10000`, `integrity_ok = true`. Свободная сумма зависит от даты запуска и календарных резервов; она не зафиксирована числом.

Демо использует текущую бизнес-дату и синтетические суммы. Загрузка отказывается работать, если хотя бы одна прикладная таблица уже содержит строки. Для личного учёта создайте отдельную пустую копию без демо и внесите собственные настройки и исходные остатки.

## Проверить установленную учебную базу

В тот же день после загрузки неизменённого демо выполните от владельца:

```bash
psql -X -v ON_ERROR_STOP=1 -f tests/native-smoke.sql
```

Содержимое файла также можно выполнить целиком через SQL-инструмент Supabase. При успехе возвращаются 12 имён проверок в `passed_checks`; при нарушении — SQL-ошибка. Тест проверяет денежные результаты, отложенные ограничения и запрет клиентского доступа. Пробные изменения откатываются, демоданные сохраняются; значения последовательностей могут увеличиться. Это проверка для отдельной учебной базы, не для рабочего учёта. [Отчёт](testing.md#supabase-validation).

## Порядок настройки

1. **Развернуть структуру.** Выполнить установку выше. Сверить объекты с [манифестом SQL](../database/manifest.json).
2. **Настроить доступ.** Выбрать авторизованный канал интеграции и проверить допустимые операции его роли. Не переносить без проверки права рабочей базы.
3. **Задать параметры расчётов.** Настроить ключи из таблицы ниже; не полагаться на резервные значения функций. В экспортируемом коде убраны индивидуальные зарплата, дата начала учёта и форматирование названия банка.
4. **Создать счета и категории.** Выбрать активный счёт оплаты по умолчанию в настройках ассистента. В текущем коде нет подтверждённого общего ключа БД для этого выбора.
5. **Задать исходные остатки.** Для денег — `account_balance_snapshots`, для тела долга — `liability_balance_snapshots`.
6. **Настроить долги.** Для кредитной карты связать долг с кредитным счётом; для кредита с графиком — с платёжным буфером и банковским графиком.
7. **Настроить регулярные события.** Проверить виды правил, даты, исключение из бюджета и привязанные счета. Затем сформировать календарь на нужный период через административный процесс.
8. **Проверить чтение.** Получить статус и диагностику. При отсутствии ближайшего дохода свободные деньги до дохода будут `null`.
9. **Проверить запись на демонстрационных данных.** Записать операцию, повторить ту же команду с тем же ключом, убедиться, что дубликат не появился.
10. **Подключить чат.** Передать ему [инструкции](chat-instructions.md), доступ к нужным функциям и правила отображения статуса. Проверить один полный сценарий через реальный канал.

Функция генерации календаря изменяет базу. Её не следует вызывать при каждом запросе статуса.

## Обязательные настройки

Перед внесением операций задайте эти ключи для своего контура. `monthly_salary` необходим, если используются активные правила `salary_advance` / `salary_balance`; без него генерация зарплатных событий выдаёт ошибку. Ключи и JSON-типы:

| Ключ `finance_settings` | Значение JSON | Для чего нужен |
|---|---|---|
| `business_timezone` | Строка с IANA-часовым поясом | Бизнес-дата, границы дня, согласование времени операции |
| `default_weekly_budget` | Число | Бюджет недели при отсутствии индивидуального значения |
| `monthly_salary` | Число | Расчёт планового аванса и остатка зарплаты |
| `tracking_start_date` | Строка даты `YYYY-MM-DD` | Начало отслеживания непогашенных повседневных расходов по кредитным картам |

В демо есть [пример заполнения finance_settings](../database/demo/seed.sql). При отсутствии `tracking_start_date` экспорт использует нейтральную нижнюю границу `1970-01-01`; для реального учёта задайте свою дату явно.

Бюджет конкретной недели задаётся в `living_budgets`; дата `week_start` должна быть понедельником. При расчёте приоритет такой: запись недели → явно переданный бюджет → настройка → встроенное значение функции.

Текущая реализация допускает только RUB для счетов, операций и правил: это ограничение БД, а не настройка интерфейса.

## Начальные остатки и исторические операции

Снимок означает: «на этот момент баланс уже равен указанному значению». Операция ровно в момент снимка повторно к нему не прибавляется; учитываются операции строго после снимка и не позже момента отчёта.

Пример: в 10:00 зафиксировано 15 000 ₽. Расход в 09:50 уже включён в этот остаток; расход 300 ₽ в 10:10 даст остаток 14 700 ₽. Если известна только дата снимка, уточните, к какому времени относится сумма.

Снимок долга и деньги на платёжном счёте — разные записи. Пополнение платёжного счёта не заменяет исходный остаток тела кредита.

## Подключение ассистента

Пакет задаёт контракт функций, но не поставляет готовую конфигурацию Actions, MCP или другого адаптера. Для выбранного клиента потребуется проверить:

- чтение статуса и справочников;
- запись `finance_command` с сохранением ключа запроса при сетевом повторе;
- отдельное действие исправления;
- доступ только к нужному финансовому контуру;
- обработку отказов доступа и ошибок валидации.

Supabase предоставляет официальный MCP-сервер, однако это само по себе не доказывает готовность настройки конкретного клиента. [Документация MCP](https://supabase.com/docs/guides/ai-tools/mcp)

## Критерий готовности собственной копии

Пользователь может получить статус, внести и исправить демонстрационный расход, увидеть изменение нужного счёта и бюджета, а затем повторить запрос без дублирования. Другой неавторизованный клиент не может читать или изменять эти данные.

Для автоматических уведомлений отдельно настраиваются расписание, часовой пояс и доступ исполнителя. Расписания из чужого чата не переносятся вместе с SQL-схемой.
