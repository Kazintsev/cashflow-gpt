# Поддержка документации для людей и агентов

> ID: documentation_maintenance · Для: developer, repository_agent · Тип: proposed_workflow
>
> Как обновлять связанные Markdown и JSON. [Карта документации](index.md) · [Манифест](manifest.json)

## Структура чтения

README объясняет проект. docs/index.md маршрутизирует по задачам. docs/agents.md описывает работу финансового агента. AGENTS.md касается разработки репозитория. llms.txt служит коротким индексом; его наличие само по себе не подключает документы к какой-либо модели.

У каждого документа в manifest.json есть стабильный id, path, audience, evidence_status и purpose. Это помогает выбирать нужный материал без загрузки всего справочника.

## Источники и версии

- Версия формата JSON-каталогов — schema_version, сейчас 1.
- snapshot_date — дата обследования БД, не дата каждого запроса пользователя.
- observed_status_version — известная версия JSON-ответа статуса, не версия установщика.
- runtime_source_in_repo=true — канонические исходники находятся в database/functions/ и database/schema/.
- source_path — путь к SQL от корня репозитория; portability_changes — явные отличия от источника.
- ready_for_clean_install=true — bootstrap проверен в PGlite и отдельном Supabase PostgreSQL 17.6; поле clean_install_validation уточняет среду. Это не готовность ИИ-адаптера.

Не повышайте достоверность документа до observed_snapshot только потому, что он написан уверенно. Предлагаемый алгоритм агента остаётся proposed_workflow до проверки конкретного адаптера.

## Как менять контракт

1. Получить авторизованные определения функций и метаданные нужной версии; записи пользователей для каталога не нужны.
2. Сопоставить типы аргументов, перегрузки, nullable-поля и возвращаемые данные.
3. Обновить соответствующий раздел API, JSON-каталог и Markdown-справочник.
4. Сохранить якорь неизменённой сигнатуры; для изменённой создать новый signature_id.
5. Обновить сценарии проверки и ограничения выпуска.
6. Если изменён SQL, пересобрать bootstrap и выполнить тесты по [порядку изменения кода](source-code.md#edit); затем проверить документы.

Сигнатуры каталогизируются по полному qualified name и identity_arguments. Имя функции без типов не различает перегрузки. Значения DEFAULT намеренно не копируются в каталог функций; has_default показывает только возможность опустить аргумент. NULL-значение и отсутствие аргумента не считаются универсально равнозначными.

## Машинные форматы

| Файл | Содержание | Не является |
|---|---|---|
| manifest.json | Документы, задачи, ссылки на сценарии и сигнатуры | Планировщиком или разрешением выполнить действие |
| reference/functions.json | Сигнатуры, параметры, результаты, класс вызова и якоря | Телами функций или конфигурацией MCP |
| reference/schema.json | Таблицы, представления, поля, ограничения и триггеры | Полным DDL, миграцией или набором данных |

Все поля doc_ref, source_path и пути манифеста отсчитываются от корня репозитория. relative Markdown-ссылки отсчитываются от файла. Рутинные функции класса internal_review_required требуют чтения реализации перед прямым использованием, даже если имя начинается с get_.

## Проверка

Из корня репозитория:

```bash
python3 scripts/check_docs.py
```

Скрипту нужен Python 3 и только стандартная библиотека. Он проверяет локальные ссылки, явные якоря, структуру каталогов, совпадение сигнатур с секциями справочника и маршруты задач.

Эта проверка не исполняет SQL, не тестирует банковскую арифметику, не проверяет доступ к рабочей базе и не загружает документы во внешние сервисы.

## Добавление документа

Добавить файл, запись documents в manifest.json и ссылки из нужного маршрута. Если документ предназначен для программного чтения, использовать стабильные ключи и явно указать границы достоверности. Не дублировать формулы без необходимости: ссылаться на главу расчётов.

При изменении состава файлов обновить release.md. Команды установки для ещё не существующих файлов не выдавать за проверенные команды.
