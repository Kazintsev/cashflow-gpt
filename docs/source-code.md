Отдельные компоненты SQL могут зависеть друг от друга: для первой установки используйте bootstrap. Он создаёт объекты в одной транзакции, временно отключая раннюю проверку тел функций из-за взаимных зависимостей. Тест затем повторно компилирует все 76 тел с включённой проверкой.

Инвентарь: 19 таблиц, 4 представления, 76 функций, 18 последовательностей, 43 дополнительных индекса, 53 пользовательских триггера. В каталоге ограничений — 144 записи: 64 CHECK, 37 FK, 19 PK, 12 UNIQUE и 12 constraint triggers. NOT NULL хранится в определениях столбцов; внутренние триггеры FK создаёт PostgreSQL.

## Происхождение и изменения переносимой версии

Определения прочитаны из каталога рабочей PostgreSQL 17 **8 сентября 2026 года**. Выгружена прикладная схема `public`, включая тела функций; записи счетов, операций, настроек и долгов не копировались. Пространства `auth` / `storage`, облачные настройки, пользователи, пароли, права исходных ролей и текущее состояние счётчиков не входят в экспорт. Последовательности начинаются с объявленного START.

Экспорт имеет три осознанных изменения тел функций:

| Функция | Поведение переносимого кода |
|---|---|
| `generate_cash_flow_events` | Зарплата берётся из `finance_settings.monthly_salary`. При активных зарплатных правилах отсутствие настройки вызывает ошибку; индивидуальная сумма из исходной базы удалена |
| `get_credit_budget_position` | При отсутствии `tracking_start_date` используется `1970-01-01`; индивидуальная дата начала учёта удалена |
| `get_status_until_next_income` | Краткое имя наличных — «нал», остальных счетов — их фактическое имя. Сортировка по типу счёта; особое форматирование личного банка удалено |

Остальные тела сохраняют исходную логику. Сигнатуры функций не изменены. JSON-справочники отражают обследованную структуру, а `source_path` ведёт к переносимой реализации. Поле `portability_changes` позволяет агенту увидеть различия без загрузки всей базы. Настройки своего учёта задавайте явно: значения по умолчанию не являются персональной рекомендацией.

## Доступ новой установки

Новая установка включает RLS на всех таблицах и отзывает права на таблицы, последовательности и функции у `PUBLIC` и существующих ролей `anon`, `authenticated`, `service_role`. Все четыре представления используют `security_invoker=true`; функции сохраняют права вызывающего. Работать с ядром можно от владельца объектов. Общие политики доступа для клиентов не поставляются.

Это намеренно отличается от обследованной рабочей базы с выключенным RLS. Исходные права не копируются, рабочая база не меняется. Поле `observed_rls_enabled` в справочнике относится к источнику, `installed_rls_enabled` — к новой установке.

Перед подключением приложения нужно отдельно спроектировать роль и её права, разрешённые операции и проверку пользователя. Не передавайте владельческие реквизиты в браузер. Модель общей базы с изоляцией нескольких владельцев пока не реализована. ## Как менять код человеку и агенту

1. Найдите нужную перегрузку в [каталоге функций](reference/functions.json) по `qualified_name` и `identity_arguments`, откройте `source_path`.
2. Прочитайте связанный контракт API и [правила расчётов](calculations.md). Для таблицы используйте `source_path` из [каталога схемы](reference/schema.json), затем общие constraints и triggers.
3. Измените канонический SQL, связанный справочник и существенный регрессионный сценарий. При добавлении файла обновите `database/manifest.json`.
4. Пересоберите и проверьте комплект из корня репозитория:

```bash
python3 scripts/build_sql.py
python3 scripts/build_sql.py --check
python3 scripts/check_docs.py
npm test
```

Установочный файл генерируется: правка только `bootstrap.sql` будет потеряна при сборке. Для изменения уже установленной базы нужна отдельная миграция обновления; повторное выполнение bootstrap её не заменяет. Проверки репозитория не применяют SQL к рабочему учёту.

## Проверенная среда и границы поставки

Свежая установка, инвентарь, компиляция и 14 проверок прошли в **PostgreSQL 18.3 через PGlite 0.5.8**. PGlite запускает PostgreSQL в WebAssembly; это реальное выполнение SQL в изоляции, без сетевого подключения к Supabase. [Документация PGlite](https://pglite.dev/docs/)

Нативный сервер PostgreSQL 17, Supabase SQL Editor / Data API, конкурентные сетевые вызовы и чат-адаптер этим тестом не проверяются. Сценарии и оставшиеся проверки перечислены в [testing.md](testing.md). Установка не включает импорт Excel, OCR, банковскую синхронизацию, секреты или расписания уведомлений.
