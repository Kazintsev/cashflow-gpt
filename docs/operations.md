# Эксплуатация и устранение ошибок

> ID: operations · Для: operator, agent · Тип: mixed
>
> Диагностика, повторы и обслуживание. [Карта документации](index.md) · [Манифест](manifest.json)

## Регулярная проверка

Выполнить в собственной базе:

```sql
select severity, code, entity_type, entity_id, message
from public.finance_integrity_check(now())
order by severity, code, entity_id;
```

Проверка ничего не исправляет. Пустой результат означает отсутствие диагностик, предусмотренных этим кодом, но не является полным аудитом безопасности или подтверждением банковского остатка.

Если проверка запускается автоматически, отдельно настройте расписание, часовой пояс, роль доступа и доставку результата. Автоматизация должна сообщать об ошибке вызова, а не выдавать её за пустой результат.

## Типовые ситуации

| Симптом / код | Что проверить | Действие |
|---|---|---|
| permission denied | Сигнатуру функции, роль клиента, права на схему и зависимые объекты | Исправить конкретный маршрут доступа после согласования; не выдавать широкие права вслепую |
| Свободные деньги = null | Есть ли незавершённый доход с датой не раньше сегодня | Проверить календарь доходов и их связи с фактами |
| Остаток отличается от банка | Время снимка, операции до/после него, правильный счёт | Сверить историю и затем исправить конкретные данные |
| `transaction_date_mismatch` | Дату операции и её время в business_timezone | Согласованно исправить дату/время |
| `category_allocation_mismatch` | Сумму операции и распределение категорий | Заменить разбиение вместе с исправлением суммы |
| `receipt_amount_mismatch` | Итог чека и расход | Исправить связанный чек и операцию |
| `receipt_items_mismatch` | Суммы строк для полностью разобранного чека | Исправить позиции; не помечать неполный чек полностью разобранным |
| `debt_detail_mismatch` | Тип операции, долг, тело + проценты + комиссия | Исправить детализацию в согласованной транзакции |
| `executed_without_full_payment` | Есть ли реальная оплата и связи payment | Подтвердить корректный факт либо исправить ложный статус |
| `overdue_unconfirmed` | Прошедшее обязательство и подтверждение списания | При покрытии подтвердить списание; без покрытия определить требуемое действие |
| `payment_buffer_shortfall` | Баланс буфера и сумма закреплённых обеспечений | Проверить переводы и распределения денег |
| `missing_liability_anchor` | Снимок тела кредита на момент отчёта | Уточнить исходный остаток долга |
| allocation exceeds… | Суммы распределений по операции и событию | Устранить превышение; не создавать компенсирующие связи наугад |
| request key…different arguments | Не используется ли старый ключ для другой команды | Для новой операции новый ключ; сетевой повтор — прежний ключ и аргументы |

`overdue_unconfirmed` имеет уровень `error`, если деньги ещё нужны, и `warning`, если обязательство обеспечено, но исполнение не подтверждено.

## Если запись завершилась тайм-аутом

1. Сохранить исходный ключ и исходный JSON.
2. Повторить `finance_command` с теми же аргументами.
3. Проверить возвращённый ID и операцию.
4. Не генерировать новый ключ, пока не выяснено, был ли первый запрос принят.

Этот порядок относится к идемпотентной обёртке. Прямой вызов функции исправления или административного генератора не получает такую гарантию автоматически.

## Если неверно указана сумма или счёт

Использовать [маршрут исправления](api.md). При связанных чеках, категориях, платёжных распределениях и деталях долга изменения должны быть согласованными. Отложенные ограничения могут отклонить транзакцию на COMMIT.

Для сверки наличных сначала проверяются последние операции и момент снимка. Новый снимок без разбора расхождения способен скрыть ошибку классификации и бюджета.

## Резервное копирование и восстановление

Для собственного контура нужен отдельный закрытый резерв данных. Установочный SQL создаёт структуру в пустой схеме, но не личную историю операций.

Процедура восстановления должна проверяться в отдельной базе:

1. Восстановить структуру и совместимую версию функций.
2. Восстановить данные и состояние последовательностей.
3. Проверить связи, ограничения и триггеры.
4. Сопоставить контрольные остатки и несколько статусов.
5. Проверить доступ клиентской роли.
6. Только после проверки переключать интеграцию.

Наличие и срок хранения управляемых резервных копий зависят от конфигурации Supabase; в рамках документации они не проверялись. Пакет не содержит проверенного backup/restore-скрипта.

## Изменение структуры

Для выпуска фиксируются SQL-миграции, описание изменения поведения и тестовые сценарии. Изменения сначала проверяются на отдельной базе. Применение к рабочему учёту — отдельное действие, а не часть чтения статуса.

При изменении возвращаемого JSON обновляются версия контракта, документация API и интеграционные проверки.
